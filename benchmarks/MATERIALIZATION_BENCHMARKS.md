# Portfolio Materialization Benchmarks

This procedure is the acceptance record for the portable portfolio
materialization path. It measures JSON validation and construction of a reusable
portfolio handle; it excludes database and network I/O, runtime startup,
market-context construction, pricing, pandas conversion, and fixture generation.
See [`CONTRACTS.md`](../docs/CONTRACTS.md#root-contract-matrix) for the persisted
envelope, generated schema, and Rust/Python/WASM API map.

## Deterministic fixtures

`finstack-quant/portfolio/benches/materialization_fixtures.rs` is the shared
generator. It alternates ten-year semiannual amortizing bonds with explicit
twenty-step remaining-notional schedules and ten-year CMS swaps carrying
twenty explicit CMS fixing, CMS payment, accrual-fraction, and funding-leg
payment rows.

- Fixture A: 5,000 positions and 5,000 unique artifacts; 14,720,177 bytes and
  15,000 normalized artifact dependencies.
- Fixture B: 5,000 positions over 50 unique artifacts; 865,774 bytes and 150
  normalized artifact dependencies.

The Rust benchmark builds these fixtures in memory. Python and Node/WASM use the
same generated bytes under `target/materialization-benchmarks`. Both binding
harnesses unconditionally run the release fixture generator before loading
those bytes; the mise tasks do so as an additional explicit prerequisite.
Generated fixtures are intentionally not checked in. Contract tests inspect
both artifact families, all serialized schedule vectors, 5,000 unique content
hashes, and the one-to-one Fixture A position mapping.

## Protocol and gates

The native acceptance probe uses release code, warm filesystem pages, a fresh
artifact cache for each cold sample, a pre-populated cache for warm
samples, and nearest-rank median/p95 over at least 100 independently timed
calls. Caches are constructed before each timer starts and are explicitly
sized to 5,000 entries for Fixture A or 50 for Fixture B in Rust, Python, and
WASM. Fixture generation, release compilation, runtime startup, fixture reads,
and cache construction are outside timed regions.

`FQ_MATERIALIZATION_P95_SAMPLES` must be a finite integer of at least 100.
`FQ_MATERIALIZATION_SMOKE=1` is the only short-run override and is intended for
tests, not acceptance records.

The elapsed boundaries are:

- Rust: the strict Rust call and creation of its returned Rust values.
- Python: `Portfolio.from_materialization` through creation of Python
  portfolio/report wrappers.
- WASM: the exported WASM call through JavaScript result conversion; handle
  cleanup is after the timer.

Binding and Rust calls run in separate executions, so their samples are treated
as independent distributions. Reported overhead is the difference between
their nearest-rank medians or p95s. Each estimate includes a deterministic 95%
independent nonparametric bootstrap interval (5,000 resamples with a
case-derived fixed seed); samples are never aligned by index.

`validateMaterialization` uses the validation-only Rust path. It performs
strict parse, limits, version, hash, reference, dependency, instrument, and
position-semantic validation. It also enforces envelope-checkable entity,
position-to-book assignment, and bidirectional book-hierarchy invariants, but
does not construct positions or rebuild a `Portfolio` index. Its report
therefore records zero for `build_positions` and `index_build`.

Run the focused measurements from the repository root:

```bash
FQ_MATERIALIZATION_P95_SAMPLES=100 cargo bench \
  -p finstack-quant-portfolio --bench materialization -- \
  --sample-size 100 --warm-up-time 1 --measurement-time 5 \
  --nresamples 1000 --noplot

FQ_MATERIALIZATION_P95_SAMPLES=100 scripts/materialization_bench.sh python

FQ_MATERIALIZATION_P95_SAMPLES=100 scripts/materialization_bench.sh wasm
```

The complete acceptance record has one orchestration command:

```bash
FQ_MATERIALIZATION_P95_SAMPLES=100 scripts/materialization_bench.sh record
```

It regenerates both fixtures, verifies the immutable checked-in Rust and Python
baseline provenance/digests, runs only current release Rust/Python/Node-WASM
measurements, applies both strict regression comparisons, invokes
`scripts/collect_materialization_results.py`, writes the machine-readable
record, and updates then verifies the Markdown artifact SHA. It never replaces
a baseline. Acceptance uses at least 100 raw calls per case.

Compact baselines under `benchmarks/materialization/` are created only by
the `rust-baseline` and `python-baseline` steps of
`scripts/materialization_bench.sh`. Both fail before measurement when the
baseline exists. Intentional replacement requires the explicit
`FQ_REPLACE_MATERIALIZATION_BASELINE=1` opt-in.

The native cold-A p95 hard gate is strictly below 1,000 ms. Cold A below
500 ms and warm B below 250 ms are engineering targets. The Python
`python-baseline` / `python-compare` steps use
isolated artifacts and reject wrong revisions, fixture digests, case sets,
paths, and stale or missing current measurements before applying the 10%
median-regression gate. The complete record stores every Python per-case median
change, its pass/fail result, and baseline artifact provenance. The focused
`rust-baseline` / `rust-compare` steps use
`target/materialization-criterion`, require the exact four expected current
paths, reject stale or unexpected artifacts, and compare against
`benchmarks/materialization/materialization-rust-baseline.json`. Neither comparison
depends on an untracked Criterion baseline directory. The
`doc-check` step verifies the record digest,
toolchains, and all baseline artifact paths, identities, and hashes without
running measurements.

## Manual allocation and peak-memory profiling

Allocation and peak-memory profiles are diagnostic runs, not CI gates. Do not
compare their latency with the uninstrumented acceptance run.

On macOS, capture peak resident memory:

```bash
cargo build --release -p finstack-quant-portfolio --example materialization_case
scripts/materialization_bench.sh fixtures
/usr/bin/time -l target/release/examples/materialization_case \
  cold target/materialization-benchmarks/materialization-a-5000-unique.json 5000
```

Use `warm` or `validation` and the corresponding fixture/capacity for another
dedicated run. The executable performs exactly one requested case; compilation,
fixture generation, and unrelated cases are excluded. Record `maximum resident
set size` from the final output. Instruments, `heaptrack`, or Valgrind Massif
should wrap this executable. No profiler crate or CI dependency is required.

When a gate misses, inspect the printed parse, version/validation, unique decode,
position build, and index build p95 values first. Add bounded parallel decoding
only when this phase evidence identifies decoding as the bottleneck and a
before/after benchmark demonstrates improvement while restoring input order.
